# llm_fund 要件定義書

作成日: 2026-07-04
ステータス: ドラフト（承認待ち）

## 1. 背景と目的

AI による取引自動化の事前調査（[feasibility-report.md](feasibility-report.md)）の結論：

- LLM に売買判断を直接させて自動執行する構成は、実資金実験（Alpha Arena 等）で軒並み損失であり非推奨
- ただし「低頻度・テキスト情報中心・現物ロングオンリー」は LLM の比較優位（文脈理解）が活きる唯一の構成
- 発見済みエッジは存在せず、本プロジェクトは**仮説検証**である

これを踏まえ、本プロジェクトは自動売買 bot ではなく、**「LLM がファンドマネージャー役として売買指示を生成し、人間が執行する投資判断システム」＋「その判断に価値があるかを厳密に測定する検証パイプライン」**を構築する。

### 目的（優先順）

1. **検証**: 「LLM の低頻度投資判断はインデックス積立・単純ルールに勝てるか」を測定可能にする
2. **規律**: 判断・執行・振り返りのサイクルを構造化し、感情による逸脱を記録・可視化する
3. **省力化**: 日次の銘柄チェックと指示生成を自動化する（人間の作業は執行のみ）

### 非目的（Non-goals）

- 自動発注（ブローカー API 連携）は行わない
- 短期・高頻度売買はしない（日次判断・IFO による日中リスク管理）
- 確実な利益の保証はしない。負けている事実が見える設計こそが成果物

## 2. 運用モデル

| サイクル | 内容 | 人間の役割 |
|---|---|---|
| **月次** | リバランス方針・取引方針の決定、ユニバース入替提案 | 方針・入替の承認 |
| **週次** | 取引振り返り、売買基準（IFO 幅等）の見直し提案 | 基準変更の承認 |
| **日次** | 監視銘柄の値動きチェック → 売買指示生成（IFO パラメータ完全指定） | 証券会社アプリで IFO 注文を執行、結果を記録 |

- 日中のリスク管理はブローカーのサーバーサイド IFO 注文（利確/損切りの自動決済）に委任する
- 指示は「銘柄・株数・エントリー価格・利確価格・損切り価格」まで完全指定し、人間が5〜10分で機械的に執行できる粒度とする

## 3. 機能要件

### FR-1 データ取得・ブリーフィング
- 監視ユニバース（設定ファイルで管理、初期10銘柄程度の日本株）の日足 OHLCV を取得しローカルにキャッシュする
- テクニカル指標（リターン、移動平均乖離、ATR、出来高比等）を構造化テーブルとして算出する
- チャート画像は LLM に渡さない（数値時系列は LLM の弱点。構造化テキストで渡す）
- 将来: ニュース見出し・決算情報を組込む（組込みまでは「価格指標のみの実験」であることをレポートに明記）

### FR-2 LLM 判断
- ブリーフィング＋現在ポートフォリオ＋月次方針＋週次基準＋過去指示の成績を入力とし、構造化出力（目標ポートフォリオ、売買指示リスト、各指示の根拠文）を得る
- 出力はスキーマ検証必須。検証不能な出力は指示として扱わない
- プライバシー: 口座残高の実額を送らず比率ベースで判断させるモードを既定とする

### FR-3 指示バリデーション（コンプライアンス層）
- 資金リスクに関わる制約は**ハード拒否**（設定で緩和不可の絶対上限をコードに持つ）:
  - 1指示の想定損失 `(entry − sl) × units ≤ NAV × x%`
  - 1銘柄組入上限、総エクスポージャー上限、現金余力、回転率上限
  - SL（損切り）未指定の拒否、ユニバース外銘柄の拒否
  - データ鮮度違反（取得失敗・古いデータ）時は `NO_TRADE` を強制
- 日本株固有制約: 売買単位（100株）、呼値、値幅制限の検証
- 拒否・警告は理由付きで全件記録する（監査ログ）

### FR-4 執行記録
- 人間の執行結果（約定価格・執行しなかった理由を含む）を記録し、指示との乖離を可視化する
- 人間が扱う指示識別子は外部識別子（ticket_no）とし、DB 内部 PK は露出しない

### FR-5 成績測定（本プロジェクトの核心）
- **仮想執行（virtual_fill）**: 全指示を保守的ルールで仮想約定させ、実行遵守と独立に LLM 判断そのものの成績を測る
  - 同一日足内で利確・損切り両方に到達しうる場合は損切り優先（保守側）
  - 手数料・スリッページ・注文有効期限・未約定を組込む
- **3者比較ベンチマーク**: LLM 運用 vs インデックス積立（TOPIX 連動 ETF）vs 単純モメンタムルールを、同一キャッシュフロー・同一コスト条件で常時比較
- 指標: NAV、最大ドローダウン、Sharpe、勝率、回転率、コスト比率

### FR-6 レビューサイクル支援
- 週次: 直近指示の成績・IFO 幅の妥当性を LLM がレビューし、基準変更を**差分＋根拠付きで提案**。人間承認で有効化、ロールバック可能
- 月次: 方針見直しとユニバース入替を提案。人間承認制

### FR-7 配信・起動
- CLI として実装（`fund daily` / `weekly` / `monthly` / `record` / `benchmark` / `fetch` / `status`）
- 起動は cron または llm_company からの trigger（第2段階で llm_company worker 統合。CLI は `--format json` で機械可読出力を提供）
- 出力: Markdown レポート（ファイル）＋任意で Webhook 通知（Discord/Slack）

## 4. 非機能要件

- **監査性**: 全 LLM 呼び出し（prompt/response 本体、モデル、トークン数、参照した方針/基準/データ）と全指示・全拒否理由を SQLite に永続化。判断の事後検証を可能にする
- **再現性**: `--no-llm` ドライラン（テンプレート判断）で LLM 課金なしにパイプライン全体をテスト可能
- **コスト**: LLM 呼び出しは日次1回＋週次/月次。月額数百円規模を想定
- **セキュリティ**: API キーは .env（コミット禁止）。Webhook 送信内容に留意（保有情報が載る）
- **単独動作**: 外部システム（llm_company）なしで cron＋ファイル出力のみで完結すること

## 5. 実資金移行ゲート（paper-only 原則）

本システムの成果物は**仮想執行のみで運用する**。実資金の投入は以下を満たした場合に、別途計画を立てて判断する：

1. 3ヶ月以上の連続運用で、仮想成績が3者比較でインデックス積立を上回る
2. 執行遵守率（指示どおりに執行した割合）が十分高く、運用が成立している
3. 最大ドローダウンが事前定義の許容値内

### 撤退基準

- 6ヶ月運用してインデックス積立に明確に劣後し続ける場合、LLM 判断部分を廃し「規律支援ツール」として再定義するか、プロジェクトを終了する

## 6. 主要リスク

| リスク | 対策 |
|---|---|
| 仮想執行の甘い判定による偽陽性（LLM が有効に見えてしまう） | 保守的約定判定（SL優先）、コスト組込み、ベンチマーク条件の統一 |
| 人間の執行不遵守で検証が無意味化 | 乖離を一級データとして記録・可視化。遵守率をレポートに常掲 |
| LLM の過学習的な基準変更（週次レビューの自己強化） | 変更は差分＋根拠必須・人間承認・ロールバック可能 |
| yfinance の非公式性（データ品質・継続性） | データ鮮度・欠損ゲート、異常時 NO_TRADE。将来 J-Quants 等へ差替可能なデータ層の抽象化 |
| ハルシネーション指示 | スキーマ検証＋ハードバリデーター＋人間執行の三重ゲート |
